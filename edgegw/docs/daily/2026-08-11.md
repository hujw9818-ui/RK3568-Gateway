## 三、踩坑记录（面试素材库）

### 坑 1：SDK 权限问题 —— ubuntu 用户无法编译

**现象**：SDK 放在 `/root/` 下，文件属主是 `ubuntu`，但 `/root` 目录只有 root 能进。buildroot 拒绝 root 编译（`configure: error: you should not run configure as root`），而 ubuntu 用户连目录都进不去。

**根因**：WSL 默认 root 登录，SDK 解压在了 root 的家目录，文件属主却混着 root/ubuntu。

**解决**：
```bash
mv /root/rk3568_linux_4.19 /home/ubuntu/
chown -R ubuntu:ubuntu /home/ubuntu/rk3568_linux_4.19
```

**经验**：嵌入式开发环境第一条铁律——**源码目录和编译用户必须一致**。buildroot 出于安全考虑禁止 root 编译。

---

### 坑 2：板子 SSH 握手超时（banner exchange）

**现象**：`ssh: Connection timed out during banner exchange`，但 ping 通、22 端口开放。

**根因**：板子 SSH 服务（dropbear）较弱，**同时开多个 SSH 会话会互相卡死**；或板子 CPU 被占满时握手响应慢。

**解决**：保持 1-2 个会话；用 `ssh root@IP` 正确语法（之前 `ssh @root IP` 被解析成用 Windows 用户名 admin 登录，密码自然不对）；必要时增加 `-o ConnectTimeout=30`。

**经验**：嵌入式板子资源有限，SSH 并发弱是常态，**别开一堆终端连板子**。

---

### 坑 3：mosquitto broker 启动后"看不到进程"

**现象**：`mosquitto -c xxx.conf -d` 后台启动后 `ps | grep mosquitto` 看不到 broker，只看到残留的 mosquitto_sub。

**根因**：`-d` 后台模式失败时错误不可见；且之前残留的 `mosquitto_sub` 进程还在（killall 没杀干净，它在别的 pts）。实际 broker 第一次前台运行是成功的。

**解决**：
```bash
# 全杀干净（含顽固进程）
pkill -9 -f mosquitto
# 用 nohup 后台，错误可见
nohup mosquitto -c /etc/mosquitto/edgegw.conf > /tmp/mosquitto.log 2>&1 &
# 用 netstat 验证真在监听
netstat -tlnp | grep 1883
```

**经验**：判断服务是否活着，**用端口监听验证（netstat/ss）比 ps 可靠**；后台服务一律 `nohup + 日志文件`，错误才看得到。

---

### 坑 4：摄像头 rkisp "update sensor failed"

**现象**：`dmesg` 显示 `rkisp-vir0: max input:0x0@0fps`、`update sensor failed`、`clear unready subdev num: 5`。

**根因**：**CSI 摄像头根本没插**（FPC 排线未接）。设备树同时使能了 os04a10/ov5695/imx415 三种 sensor，靠 I2C 读 ID 匹配；没插摄像头自然全部失败。

**解决**：插上摄像头（断电操作）后重启，日志变为 `ov5695 2-0036: Detected OV005695 sensor` + `Async subdev notifier completed`——识别成功。

**经验**：RK3568 的 rkisp 会注册多个 video 节点（mainpath/selfpath/rawwr/statistics），**真正出图的是 `rkisp_mainpath`（/dev/video0）**；查摄像头先看 `dmesg | grep -iE 'sensor|camera'`，别猜。

---

### 坑 5：gstreamer 插件缺失

**现象**：
- `no element "rkcamsrc"` —— gstreamer-rockchip 插件没编进镜像
- `no element "multipartmux"` —— gstreamer-good 的 multipart 插件被裁剪

**根因**：Buildroot 2018.02 镜像裁剪了部分 gstreamer 插件，只保留了基础 + rockchipmpp（硬件编解码）。

**解决**：**用标准插件 v4l2src + 硬件编码插件 mpph264enc**（这些在）：
```bash
gst-launch-1.0 v4l2src device=/dev/video0 \
  ! video/x-raw,format=NV12,width=1280,height=720 \
  ! mpph264enc ! h264parse ! mp4mux \
  ! filesink location=/tmp/test_h264.mp4
```

**经验**：用 gstreamer 前先 `gst-inspect-1.0 | grep 插件名` 确认存在；RK 平台视频链路用 **v4l2src（采集）+ mpph264enc（硬件编码）** 是标准组合。

---

### 坑 6：`Device or resource busy` —— 摄像头被占

**现象**：第二次跑 gst-launch 报 `S_FMT failed for NV12: Device or resource busy`。

**根因**：**之前测试的 gst-launch 进程还占着 /dev/video0**（按 Ctrl+Z 暂停而不是杀掉）。

**解决**：
```bash
pkill -9 -f gst-launch
fuser -v /dev/video0   # 确认空闲
```

**经验**：**V4L2 设备是独占的**，一个进程占用后其他进程打不开；用 `fuser` 查谁占着设备。

---

### 坑 7：mpph264enc 属性名错误

**现象**：`no property "header-repeat" in element "mpph264enc0"`。

**根因**：mpph264enc 的正确属性是 `header-mode`（枚举：first-frame / each-idr），不是 header-repeat。

**解决**：
```bash
gst-inspect-1.0 mpph264enc | grep -i header   # 先查属性名
# 正确用法: 每个关键帧都带 SPS/PPS
! mpph264enc header-mode=each-idr
```

**经验**：**gstreamer 元素属性先 `gst-inspect-1.0 <元素>` 查**，别凭记忆写。H.264 裸流给中途接入的客户端必须 each-idr（每关键帧带参数集），否则解码器报 `non-existing PPS`。

---

### 坑 8：H.264 流 ffmpeg 拉流验证失败

**现象**：
- 裸 H.264 TCP 流：`Invalid data found when processing input`
- MPEG-TS 流：`non-existing PPS 0 referenced`（加 each-idr 后消失，但 `decode_slice_header error`）
- RTP/UDP 流：`Invalid data found when processing input`

**根因**：
- 裸流无容器/同步信息，ffmpeg 无法直接识别
- TS 流从中间切入错过关键帧（虽然 each-idr 后参数集重复，但 slice 仍可能因起始不对齐报错）
- RTP 流需要 SDP 描述文件才能识别 payload 类型

**解决**：视频流验证**收敛到已验证的能力**：单帧 JPEG 出图 ✅ + H.264 硬件编码录制 mp4 ✅。**Web/Qt 双端播放留到网关程序里实现**（网关程序用 ffmpeg/gstreamer 拉流 → 转 MJPEG over HTTP → 浏览器/Qt 显示），不在命令行死磕流协议。

**经验**：**分清"验证能力"和"实现产品"**。命令行能验证"摄像头出图、编码、录制"，但"双端播放"是应用层的事，应该写在网关程序里而不是命令行管道里。6 天项目要控制时间投入，视频是加分项不是红线。

### 坑 9：yaml-cpp 配置模块三次迭代（重点）

**现象链**：
1. v1 裸指针版：`Segmentation fault`
2. v2 值拷贝版：不崩了，但 `terminate called after throwing YAML::BadSubscript` → Aborted
3. v3 全防御版（try-catch 包满）：不崩了，但多级键（mqtt.host）全部读不到，返回默认值
4. v4 展平 map 版：**全部正确** ✅

**根因**：
1. v1：`&(*node)[part]` 取的是 **operator[] 返回的临时对象地址**，临时对象销毁后指针悬空 → 段错误。
2. v2：yaml-cpp 的 `operator[]` 在异常情况（空节点取子键）会抛 `YAML::BadSubscript`，而 `FindNode` 调用在 try 块**外面**，异常冒泡到 main → terminate。
3. v3：yaml-cpp 0.6.x 的 **const Node::operator[] 链式赋值 bug**——成员变量 Node 上 `node = node[part]` 逐级下钻，**子节点关联会丢失**（诊断实验证明：局部变量一次性链式 `root["mqtt"]["host"]` 完全正常，但类成员逐级查找失败）。

**解决（最终方案）**：**Load 时一次性遍历展平为 `std::map<std::string, std::string>`**：

```cpp
// Load: YAML::LoadFile → 递归遍历 → kv_["mqtt.host"] = "192.168.5.80"
// Get:  直接查 map, 快、安全、无坑
std::string host = cfg.GetString("mqtt.host", "127.0.0.1");
int port = cfg.GetInt("mqtt.port", 1883);
```

**经验**：
1. **裸指针 ≠ 安全指针**：对临时对象取地址必然悬空，能不用指针就不用。
2. **第三方库调用必须防御**：凡是调库（yaml-cpp/JSON 解析）的地方 try-catch 兜底，异常返回默认值而不是崩溃。
3. **库有 bug 时换架构绕开**：yaml-cpp 0.6.x 的 operator[] 链式有坑，展平 map 方案一劳永逸，还更快。
4. **排查段错误的正确姿势**：没有 gdb 时用"**打印定位法**"（每步 fflush + 标记行），二分定位崩溃点；再写**独立诊断程序**直接调库 API，区分"库的问题"还是"自己代码的问题"。

### 6.2 网络拓扑与双通道

板子有**两条独立网络通道**，互不干扰：

```text
eth0 (网线)  = 192.168.5.80    ← SSH 调试通道 (电脑访问板子)
wlan0 (WiFi) = 172.20.10.3     ← ESP8266 对接通道 (连手机热点)
```

**关键认知**：SSH 走网线，WiFi 是独立通道——板子连手机热点不影响 SSH。ESP8266 连热点后，broker 地址填板子的 WiFi IP（172.20.10.3），不是网线 IP。

### 6.3 踩坑记录（续）

#### 坑 10：WiFi 连不上 —— wpa_supplicant 缺 ctrl_interface

**现象**：`wpa_cli -i wlan0 status` 报 `Failed to connect to non-global ctrl_ifname: No such file or directory`。

**根因**：配置文件 `/etc/wpa_supplicant.conf` 缺少 `ctrl_interface=/var/run/wpa_supplicant` 这一行，wpa_cli 找不到控制接口。

**解决**：配置文件第一行加 `ctrl_interface=/var/run/wpa_supplicant`，重启 wpa_supplicant。

**经验**：wpa_supplicant 没 ctrl_interface 能连网，但 wpa_cli 无法查询状态——排查 WiFi 问题必须用 wpa_cli。

#### 坑 11：wpa_supplicant 卡在 SCANNING

**现象**：`wpa_state=SCANNING` 不动，连不上热点。

**排查**：
```bash
wpa_cli -i wlan0 scan          # 触发扫描
wpa_cli -i wlan0 scan_results  # 看结果
```

输出里有目标热点 `iat的iPhone`（2.4G，信号 -71）→ 板子看得到但连不上。

**根因**：对方手机热点信号弱（-71 dBm）+ 可能频段/加密兼容问题。换自己的热点 `HHH`（信号好）一次就连上。

**经验**：WiFi 连接排查三步走——先 `scan_results` 看能不能**扫描到**（没看到=物理/频段问题），再 `status` 看**wpa_state**（SCANNING=扫描中，ASSOCIATING=关联中，4WAY_HANDSHAKE=认证中，COMPLETED=完成）。

#### 坑 12：udhcpc 拿不到 IP（卡在 broadcasting discover）

**现象**：`udhcpc -i wlan0` 一直 `broadcasting discover` 没有响应。

**根因**：`wpa_state` 还没 COMPLETED（还在 SCANNING/关联中），udhcpc 提前运行拿不到 IP。

**解决**：必须先等 `wpa_cli status` 显示 `wpa_state=COMPLETED`，再 `udhcpc -i wlan0` 拿 IP。

**经验**：WiFi 连接顺序：wpa_supplicant 认证（COMPLETED）→ udhcpc 拿 IP（inet addr 出现）→ 才能用。顺序错了会一直卡。

#### 坑 13：pkill -f 误杀进程

**现象**：`pkill -f edgegw` 把 mosquitto 也杀了。

**根因**：`-f` 是匹配完整命令行。mosquitto 的启动命令 `mosquitto -c /etc/mosquitto/edgegw.conf` 包含 "edgegw" 字样（配置文件路径），所以被误杀。

**解决**：用 `pkill -x 进程名`（精确匹配可执行文件名）或 `kill $(pidof 进程名)`。

**经验**：pkill 的 `-f` 参数会把匹配范围扩大到命令行参数，危险。生产环境用 `-x` 或 `pidof`。
