## 二、电机干扰问题排查全记录（重点复盘）

### 2.1 现象演变

| 阶段 | 现象 |
|---|---|
| 最初 | 电机开正常，按停止按钮 → ESP8266 wdt reset（死机） |
| 后来 | 电机转动时**任何 MQTT 命令**（含 LED/蜂鸣器）→ 单片机挂 |
| 极端 | 电机转动时遮挡红外触发报警 → 也挂 |
| 关键 | **拔掉 TB6612 电源后，同样的代码、同样的操作 → 完全不挂** |

### 2.2 尝试过的修复（全部记录，供复盘）

| # | 方案 | 结果 | 结论 |
|---|---|---|---|
| 1 | PWM 引脚 PA8 → PA11 | 无效 | 不是引脚相邻干扰 |
| 2 | PWM 引脚 PA11 → PB8（芯片另一侧） | 无效 | 同上 |
| 3 | PWM 频率 1kHz → 100Hz | 无效（且 100Hz 电流纹波更大，方向错误，已改回） | 不是频率问题 |
| 4 | 停止方式：刹车 → 只降 PWM 滑行 | 无效 | 不是停止逻辑 |
| 5 | 独立供电：ST-Link 5V / 串口 5V / 电压模块 | 全部无效 | 不是电源来源（共地没解决） |
| 6 | 借鉴同学：非阻塞软停状态机 + 命令解耦（MQTT 路径不直接操作电机） | 部分改善 | 架构改进有效但电气干扰仍在 |
| 7 | 借鉴同学：PWM 先归零、方向后释放、先方向后 PWM | 无效 | 软件层面已做到位 |

### 2.3 决定性证据

**1. 拔电源实验（toggle 证明）**
```
TB6612 VM 接上 + 电机转 + 发命令 → 挂
TB6612 VM 拔掉 + 同样的代码 + 发命令 → 不挂
```
唯一变量是电机电源，故障随它出现/消失 → **根因是电机侧的电气干扰**（地弹/反电动势/传导干扰打到 ESP8266 供电或地线），不是代码逻辑。

**2. ESP8266 串口日志证据**
```
AT+CIPSEND=152 → OK → > → Recv 152 bytes → SEND OK   ← 命令发送成功
然后立刻: rst cause:4, wdt reset                        ← ESP8266 软件看门狗复位
```
- `rst cause:4` = 软件看门狗复位（不是欠压 cause:2）——但结合拔电源实验，判断是电机干扰导致 ESP8266 内部状态异常
- `boot mode` 每次不同（3,6 / 3,0 / 3,1）→ GPIO0 接触不良也是不稳定因素之一

### 2.4 同学代码分析（借鉴过程）

| 同学 | 方案 | 可借鉴点 |
|---|---|---|
| 同学 A（FreeRTOS） | MotorTask 独立任务 + 命令队列 + 2%/25ms 软停 + 有界 UART 等待 + 硬件复位脚 | 命令路径不直接操作电机；软停；UART 等待全部有超时 |
| 同学 B（dianji.c） | 1kHz PWM、PA8、停止时同时拉低方向脚 | 硬件布局与电源处理不同 |

**移植到裸机的部分**：命令只更新目标状态 + 主循环渐变状态机 + 停止先 PWM 归零。这些是正确方向，但最终证明**电气干扰不是软件能根治的**。

### 2.5 最终决策

在无多余元器件（无电容、无续流二极管）、时间紧迫的前提下：
- 星型接地方案需要重新布线，用户已试多种电源无效
- **决策：删除直流电机功能**，保留 LED/舵机/蜂鸣器/传感器/视频
- 全链路清理：单片机固件 + Qt + Web

## 四、Qt 光照显示修复（附带完成）

**问题**：Web 端做了 `4095 - light` 反转（光敏电路反向：挡光 ADC 值变大，反转后挡光显示变小更直观），Qt 端直接显示原始 ADC 值，两端不一致。

**修复**（`qt-client/mainwindow.cpp`）：
```cpp
// 改前: 直接显示原始值
valLight_->setText(QString::number(dev.value("light").toDouble(), 'f', 0));
// 改后: 与 Web 端一致反转
double raw = dev.value("light").toDouble();
valLight_->setText(QString::number(4095 - raw, 'f', 0));
```
交叉编译通过并部署。

## 五、经验教训（答辩/复盘素材）

1. **"时好时坏"的故障优先怀疑电气**：电机一转就挂、拔电源就好，这类 toggle 证明直接指向硬件，不要反复改软件
2. **复位原因要分清**：ESP8266 `rst cause:4`(软件看门狗) vs `cause:2`(欠压) 含义不同，但结合拔电源实验才能定论
3. **嵌入式大电流负载的铁律**：电机/舵机等感性负载必须独立供电 + 共地处理好 + 续流保护，与 MCU 逻辑电路隔离；本次因无元件无法根治，选择功能降级
4. **功能降级是合理决策**：答辩时系统稳定 > 功能齐全，删掉一个不稳定功能换取整体可靠性是工程取舍
5. **借鉴同学代码要分清"可移植的架构"与"不可移植的硬件条件"**：软停/命令解耦是对的，但同学的稳定可能源于他的电源/布线条件
