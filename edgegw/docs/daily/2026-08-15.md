## 二、核心 Bug：AT 超时只有标称值的 1/20（今天最大发现）

### 现象

单片机烧录后永远连不上热点（蜂鸣器 3 声 = AT 测试失败）。换热点、改密码、查信号全无解。

### 根因

`esp8266.c` 的等待函数用忙等计数当延时：

```c
static int wait_line(const char *expect, int tout_ms) {
    tout_ms /= 10;
    while (tout_ms-- > 0) {
        ...消费串口数据...
        for (volatile int i = 0; i < 7200; i++);   // ← 实际只有 ~0.4ms！
    }
}
```

72MHz 下 `for(7200)` 只有 **~0.4ms**，而代码假设每个 tick 是 10ms。**所有 AT 超时实际只有标称值的 1/20**：

| 指令 | 标称 | 实际 | 后果 |
|---|---|---|---|
| CWJAP 连 WiFi | 8s | ~400ms | 热点认证要 1-3s → 永远等不到 → 连不上 |
| CIPSTART TCP | 6s | ~300ms | TCP 建立要几百 ms → 经常失败 |
| 等 `>` 发数据 | 1s | ~50ms | 稍慢就超时 |
| SEND OK | 3s | ~150ms | 经常超时 |

**这解释了全部历史现象**：
- 08-14 "命令时灵时不灵"——快时刚好过，慢时失败
- iPhone 热点认证快（~500ms）勉强能用
- 安卓热点认证慢（1-3s）→ 必然失败

### 修复

忙等换成 SysTick 精确延时（项目自带的 Delay 模块，阻塞式轮询 COUNTFLAG）：

```c
while (ticks-- > 0) {
    ...消费串口数据...
    Delay_ms(10);   // SysTick 精确 10ms，期间 USART 中断照常收数据
}
```

### 教训

**嵌入式延时永远用硬件定时器，不要用指令数估算忙等**。编译器优化级别、时钟频率改动都会让忙等彻底失真，而且这种 bug 不报错、时好时坏，最难查。

## 三、ESP8266 半开连接卡死 + 软复位兜底（借鉴同学方案）

### 问题

断线后重连永远失败，之前只能**拔 ESP8266 供电**恢复。同学的 FreeRTOS 项目注释一针见血：

> "模块内部 MQTT/TCP 状态机可能卡死（半开连接），直接重发 AT+MQTTCONN 永远失败，只有复位模块才能恢复——这就是之前连不上时必须拔 ESP8266 供电重新上电的原因。"

### 修复（三层机制）

1. **开机先软复位**：`AT+RST` 等 `ready` 后关回显（ATE0），清掉上次残留状态
2. **重连失败 3 次自动软复位**：`try_reconnect()` 直接重连 3 次失败 → `AT+RST` → 重连 WiFi → 再连
3. **断线快速发现**：`CLOSED` 字节序列在 USART 中断里检测（状态机），主循环 100ms 内感知断线（原来要等 9-12 秒上报失败才察觉）

### 踩坑：`+++` 反而把模块搞挂

软复位前先发 `+++`（退出透传）——自作聪明。结果模块进入"**只回显不响应**"状态：UART 层活着（收到的字节全回显），但 AT 解析器完全不响应任何指令。串口证据：`+++AT+RST` 连在一起，之后所有指令无 OK/ERROR 应答。

**教训**：`+++` 是退出透传专用指令，模块状态异常时起反效果。删除后恢复正常。

### 附："1 分钟前发的指令现在才反应"根因链

用户最早报告的指令延迟问题，完整根因链（三层叠加）：

| # | 环节 | 根因 | 修复 |
|---|---|---|---|
| 1 | 断线发现慢 | CLOSED 只在 AT 响应处理时被消费检测，主循环空闲时断线要等 9-12 秒（3 次上报失败）才察觉 | 中断级 CLOSED 状态机，100ms 感知 |
| 2 | 重连阻塞长 | 断线后 connect_mqtt 串行执行 CWJAP(15s)+CIPSTART(10s)+3×CIPSEND(各7s)，最坏阻塞 ~51 秒，期间命令全部积压 | 超时精确化 + 失败词立即返回 + 跳过已连 WiFi |
| 3 | 半开连接卡死 | 模块内部 TCP 状态机卡死，重连指令全部无效 | 软复位兜底（AT+RST） |

三层叠加 = 断线后 1 分钟级恢复时间，命令延迟即来源于此。三层修复后恢复时间压缩到 10-20 秒。

## 四、板子 WiFi 自启修复：驱动加载时序（两轮修复）

### 现象

板子重启后 `wpa_supplicant` 进程不存在，热点里看不到板子。

### 根因

- `S36load_wifi_modules` 加载的是 **bcmdhd.ko**（板载 WiFi），但实际用的是 **USB 的 rtl8723du**
- rtl8723du 驱动注册慢且**时间不稳定**：dmesg 实测第一次 28 秒、第二次 62 秒才注册
- `S98wifi` 开机执行时 wlan0 还不存在 → `wpa_supplicant -i wlan0` 直接失败退出

### 第一轮修复（固定等待 40 秒）—— 失败

```sh
CNT=0
while [ ! -d /sys/class/net/wlan0 ] && [ $CNT -lt 40 ]; do
    sleep 1
    CNT=$((CNT+1))
done
```

重启验证时发现驱动这次花了 **62 秒**，40 秒等待仍然不够，wlan0 出现了但没人拉起 wpa_supplicant。

### 第二轮修复（后台守护）—— 最终方案

固定等待永远追不上不稳定的驱动加载时间，改为 **S98wifi 立即返回 + 后台守护进程**：

```sh
# 后台守护: 循环等 wlan0 出现 (最多 5 分钟), 出现就连接。
# S98wifi 本身立即返回, 不阻塞启动流程。
( CNT=0
  while [ ! -d /sys/class/net/wlan0 ] && [ $CNT -lt 300 ]; do
      sleep 1
      CNT=$((CNT+1))
  done
  ...拉起 wpa_supplicant + DHCP + 修默认路由...
  # 首次连接失败 (热点没开): 再后台循环等 COMPLETED (最多 20 分钟)
) &
```

**教训**：嵌入式启动脚本不要用固定延时等异步资源（驱动加载、USB 枚举），用"守护进程轮询 + 长超时"模式，彻底免疫时序抖动。

## 五、硬件教训：GPIO0 接触不良 = 随机 boot 卡死

### 现象

ESP8266 时好时坏：有时 AT 指令响应正常，有时完全无响应，串口看到：

```
ets Jan  8 2013,rst cause:4, boot mode:(3,0)
wdt reset
load 0x40100000, len 6960, room 16
...
csum 0xde
```

boot 日志在 `csum 0xde` 处戛然而止——**没有 `2nd boot version`、没有 `ready`**，固件没加载成功。

### 分析

- `wdt reset` = 每次上电都看门狗复位
- boot mode (3,0) 与正常的 (3,6) 不一致 = 启动引脚电平不稳
- 同一模块两次 boot mode 不同 = **GPIO0/接线接触不良**（杜邦线松动）

### 教训

1. ESP8266 的 GPIO0 必须 10K 上拉 3.3V，悬空 = 随机进 UART 下载模式
2. CH_PD(EN) 必须接 3.3V，GPIO15 必须 10K 下拉
3. 软件排查半天，最终是杜邦线重插解决——**嵌入式问题先查供电和接线，再怀疑代码**

## 六、架构决策：不上 FreeRTOS

对比同学的 FreeRTOS 方案（6 任务 + 收发分离 + AT 固件 MQTT 指令）后决定**保持裸机**：

| 维度 | 裸机（本方案） | FreeRTOS（同学） |
|---|---|---|
| 命令实时性 | 100ms 轮询，够用 | 任务调度，更强 |
| 断线恢复 | 软复位兜底（一样） | 软复位兜底（一样） |
| 移植成本 | 0 | SysTick/中断优先级/堆全要动 |
| 适用场景 | 单链路简单应用 | 多传感器并行/长阻塞流程 |

**决策依据**：本项目的痛点是"半开连接卡死"（软复位解决）和"超时失真"（精确延时解决），都不是 RTOS 能解决的。裸机 + 中断接收 + 软复位兜底更轻量。答辩话术：嵌入式项目够用优先，把复杂度留给真正需要的场景。

## 七、MQTT 链路诊断工具（手写 Python 客户端）

WSL 没有 mosquitto 客户端、没有 paho，手写了一个最小 MQTT 3.1.1 客户端（纯 socket）：

- CONNECT/SUBSCRIBE/PUBLISH 报文手工构造
- 踩坑：SUBSCRIBE 固定头必须是 0x82（QoS1 标志位），`8 << 4 = 0x80` 会被 broker 直接断开
- 用途：订阅 `iotgw/v1/dev/#` 监听单片机、模拟下发命令测 ack、统计 report 频率判断在线状态

这个工具成了今天的"眼睛"，所有端到端验证都靠它。

## 八、单片机 main.c 编码事故（复盘）

修改中文 SSID 时用 ASCII 编码读写整个文件，所有中文注释变成 `?`（1249 个）。恢复过程：

1. 从 main.o 的 DWARF 调试信息提取编译时源码行（`WIFI_SSID "HHH"` 等字符串）
2. 结合开发日志的功能描述重建全部注释
3. 文件编码定为 **UTF-8 with BOM**（Keil 5 和 VS Code 都能正确显示，之前的无 BOM GBK 在 VS Code 里乱码）

**教训**：
1. 改中文文件永远不要用 ASCII 编码读写
2. 中文 SSID 在 ESP8266 AT 指令里需要 UTF-8 字节序列（`\xE7\x9A\x84`），源文件编码与字符串字节的关系要先想清楚
3. 最终方案：热点名统一英文（`jang_phone`），从根上规避编码问题
