## 二、核心 Bug 修复：videoflip 漏加在主流管道

**现象**：新版 edgegw 部署后，gst 管道里没有 videoflip，视频画面仍横躺。

**根因**：昨天给推流管道加 videoflip 时，只加在了**重试管道**（pipeline_retry，首次推流失败才走），**主流管道漏加了**。

```cpp
// ❌ 主流管道 (Start() 首次推流) - 漏加 videoflip
" ! mppjpegenc ! multifilesink location=" + FramePath() + ...

// ✅ 重试管道 (首次失败才走) - 有 videoflip
" ! videoflip method=counterclockwise ! mppjpegenc ! multifilesink ..."
```

**结果**：首次推流成功 → 走主流管道 → 无 videoflip。只有首次失败重试才会旋转。

**修复**：主流管道补加 `" ! videoflip method=counterclockwise"`（与重试管道一致），重新编译部署。

**验证**：
- 抓帧尺寸 640x480 → 480x640（旋转 90° 生效）
- look_at 分析：画面正立，无横躺

## 三、踩坑记录

### 坑 1：8080 冲突真凶 = S99 自启的旧版 edgegw

**现象**：新 edgegw 启动报 `bind: 98`（EADDRINUSE），8080 被占。

**真凶**：开机自启脚本 `S99edgegw` 拉起的**旧版 edgegw**（pid 683，09:33 开机时自动启动）。昨天 `pkill -x edgegw` 没杀掉是因为当时根本没查清进程，今天 `ps -ef` 直接看到 pid 683。

**解决**：`pkill -9 -f edgegw`（注意会误杀 mosquitto，因为 edgegw.conf 匹配）→ 重启 mosquitto → 启动新版。

**教训**：板子重启后 S99 会自动拉起旧版，部署新版前必须先杀旧进程，否则 scp 会 Text file busy。

### 坑 2：WSL ssh 连板子 banner 超时（误判一上午）

**现象**：`Connection timed out during banner exchange`，TCP 22 通但收不到 SSH banner。

**真相**：**dropbear 响应慢**（超过 6 秒才回 banner），不是连不上。我之前 ConnectTimeout 设 6-8 秒太短，误判成"板子 sshd 挂了"，绕了一大圈（试 adb/telnet/expect 免密）。

**解决**：ConnectTimeout 设 25 秒就通。Windows ssh 和 WSL ssh 都能连。

**教训**：banner 超时不等于连不上，先加大超时重试再下结论。

### 坑 3：板子没有 curl

**现象**：`-sh: curl: not found`，无法在板子上用 curl 调 API。

**解决**：从 WSL 用 curl 操作板子 HTTP API（WSL 网络到板子 8080 是通的，只是 22 慢）。打通了"agent → WSL curl → 板子 API"的全自动通道，后续无需用户在板子上手敲 API 命令。

### 坑 4：PowerShell 转义地狱（工具层面）

**现象**：`|`、`$(nproc)`、`%{...}` 等被 Windows PowerShell 抢先解析。

**解决**：整条 bash 命令用**单引号**包裹传给 `wsl bash -c`；expect 脚本写文件避免引号嵌套。

### 坑 5：录像与推流抢 /dev/video0

**现象**：录像 API 返回成功但 mp4 0 字节。

**根因**：rkisp 主通道只能开一个，录像 v4l2src 和推流进程同时抢 /dev/video0，录像打开设备 EBUSY。

**解决**：`StartRecord()` 录像前自动停推流（`StopProcess`），`StopRecord()` 录完自动恢复推流（`Start()`）。

### 坑 6：qv4l2 工具占用设备（隐藏元凶）

**现象**：录像修复后仍 0 字节，手动测试报 `Device or resource busy`。

**根因**：之前调试摄像头开的 **qv4l2 GUI 工具**（pid 1067）一直占着 /dev/video0，`fuser /dev/video0` 才发现。

**教训**：诊断设备忙时，用 `fuser /dev/video0` 查占用者，别只看 gst/edgegw 进程。

### 坑 7：录像管道缺 -e 参数（SIGINT 不写 moov 头）

**现象**：设备释放后，`num-buffers=30` 手动录像能产出（163KB），但 API 无限录像仍 0 字节。

**根因**：gst-launch 默认收到 SIGINT 直接停 pipeline（不发 EOS），`mp4mux faststart` 收不到 EOS 就不写 moov header。`num-buffers` 会触发 EOS 所以能成。

**解决**：录像管道加 `-e`（eos-on-shutdown），SIGINT 时强制发 EOS。

**验证**：API 端到端录像 → 622KB mp4，H.264 High Profile 480x640，6.69 秒。

## 六、视频流卡顿根因分析（为什么同学不卡我们卡）

### 6.1 我们的卡顿根因链（4 个叠加）

| # | 根因 | 表现 | 修复 |
|---|------|------|------|
| 1 | **主循环 150ms**：`Poll(50)×2+usleep(50ms)` → PushStreamFrame 每 150ms 一次 | 推帧上限 6.6fps | Poll(10)×2+usleep(10ms)，周期 30ms |
| 2 | **JPEG 帧 150KB**（默认高质量），读文件+发送都慢 | 每帧处理耗时长 | `mppjpegenc quant=5`，帧降到 17KB |
| 3 | **帧文件在 eMMC**（data/runtime/），磁盘 I/O 慢 | 读写延迟 | 改 `/tmp/iotgw-camera`（tmpfs 内存盘） |
| 4 | **multifilesink 周期性文件消失窗口**（每 3-4 秒 0.2-1s） | 画面周期冻结 | WebServer 帧缓存兜底（MISSING 时推上一帧） |

### 6.2 同学方案为什么稳（对照他代码）

| 参数 | 我们的方案（卡） | 同学方案（不卡） |
|------|-----------------|-----------------|
| 帧率目标 | 15fps（每帧预算 66ms，无容错） | **10fps**（每帧预算 100ms，容错大） |
| JPEG 大小 | 150KB/帧（2.25MB/s 负载） | **17KB/帧**（170KB/s，快 13 倍） |
| 帧文件位置 | eMMC 磁盘 | **/tmp tmpfs 内存盘** |
| 推帧节流 | 66ms | **100ms** |
| 录像容器 | mp4mux faststart（等 EOS 才落盘，中断 0 字节） | **matroskamux**（EBML 流式边写边落盘） |
| 旋转 | videoflip 软件旋转（25-30% CPU）→ mpp rotation（3.5fps 更差） | 不旋转 |
| 旋转方案 | 服务端 | 客户端（Qt QImage rotate + Web CSS rotate） |

**本质教训**：我们追求"15fps 高质量"，链路每个环节（主循环/磁盘/网络）都卡在预算边缘，任何抖动都积累成卡顿。同学"10fps 够用"哲学，每环节留大余量，所以稳。**嵌入式项目，够用 > 极致。**

### 6.3 验证结果（最终方案）

| 验证项 | 结果 |
|--------|------|
| MJPEG 流帧率 | 6.6fps → **10fps 稳定**（双端流畅）✅ |
| JPEG 帧大小 | 150KB → **17KB**（quant=5）✅ |
| 帧文件 | /tmp tmpfs ✅ |
| 双端（Web+Qt） | 流畅，方向正立（客户端旋转）✅ |

## 七、推流控制权限重构（朋友架构观点）

**问题**：前端"停止推流"按钮直接调 `/api/camera/stop` 杀掉网关 gst 推流进程。多客户端场景下，Web 断开视频会让 Qt 也断流，且推流控制权在前端手上，违背分层原则。

**修复**：
1. **前端/Qt**："停止推流"只断开自己的 MJPEG 连接（`img.src=''` / `streamReply_->abort()`），不调网关 API
2. **网关**：推流生命周期由网关管理——客户端连接 `/api/camera/stream` 时自动启动推流；`MG_EV_CLOSE` 回调移除客户端（连接释放前指针安全），全部断开后自动停推流
3. 多客户端独立：一个断开不影响其他客户端；显式 `/api/camera/stop` 仍保留（录像前自动停推流用）

**关键坑**：mongoose 连接关闭后内存被 free，保存的指针悬空（is_closing 读悬空内存）。正确做法是在 `MG_EV_CLOSE` 事件里移除（此时 `mg_call` 尚未 free）。

**验证**：无客户端不推流 → 连接流自动推流 → 断开自动停流 ✅ 全闭环。

## 八、网络拓扑踩坑：热点抢默认路由

**现象**：板子连手机热点后，网线网络 ssh 全部失败（`No route to host` / `Connection closed`），板子"失联"。

**根因**：`udhcpc -i wlan0` 获取热点 IP 时**覆盖了默认路由**（`default via 172.20.10.1 dev wlan0`），板子回包全走热点出口，网线网络的回包断了。

**修复**：`S98wifi` 脚本的 udhcpc 加 `-R`（不设置默认路由）+ `route del default dev wlan0` 兜底。默认路由保持 eth0，热点只做直连网段（组员单片机走热点连板子，不经过默认路由）。

**最终网络**：
```text
eth0: 192.168.5.80 (默认路由, 网线, PC/WSL 访问)
wlan0: 172.20.10.3 (热点 HHH, 组员 ESP8266 连此 IP 的 broker)
```
